# Резервное копирование всей платформы

## Из кабинета директора

Откройте `/director.html`, войдите и найдите **Platform backup / Резервная копия платформы**. Задайте отдельный пароль длиной 16–256 символов, повторите его и нажмите «Создать и скачать зашифрованную копию». Пароль не записывается в журнал и не передаётся в URL. Не присылайте его в чат. Скачанный файл `.klrb` храните на другом устройстве/в защищённом отдельном хранилище, пароль — отдельно. Без пароля файл не восстановить.

В файл включаются:

- Реестр компаний, их тарифы и статусы, настройки и история.
- Базы всех инициализированных компаний: владельцы, работники, клиенты, объекты, задания, время, отчёты и настройки сайта.
- Все изображения, на которые ссылаются базы: публичные логотипы/фото и приватные рабочие фотографии.
- Финансовый журнал платформы, аннулирования и сохранённые месячные снимки.
- Известная приложению конфигурация запуска: адреса, хеш пароля директора; в подключённой демонстрации — также база основной установки и её текущая конфигурация, включая секреты/настроенные почтовые параметры. Поэтому резервную копию нужно защищать как доступ к системе.

Новые компании, в которых база ещё не создана, сохраняются в реестре как неинициализированные. Если компания уже запускалась, а её база пропала, копирование завершается ошибкой. Незарегистрированные каталоги, старые резервные копии, файлы окружения за пределами известной конфигурации и неиспользуемые изображения не включаются. История предыдущих резервных копий не размножается внутри каждого файла.

На время создания устанавливается режим обслуживания: новые запросы получают временный отказ; текущие запросы завершаются, дочерние процессы компаний останавливаются. Базы копируются через SQLite backup, затем копируются относящиеся к ним изображения. Основная демонстрация тоже ждёт завершения запросов и фоновой отправки писем. Компании снова запускаются при следующем обращении. Если запросы не завершились за установленное время, копирование отклоняется. Любые посторонние процессы, которые пишут в те же базы/папки, должны быть остановлены оператором отдельно.

Используется шифрование AES-256-GCM с отдельной случайной солью и IV на каждую копию, ключ получается через scrypt. Расшифровка сначала проверяет подлинность целого файла, затем пути, контрольные суммы SHA-256, структуру реестра и целостность SQLite/ссылки на изображения. Восстановление из недоверенных файлов не выполняет их код. Шифрование использует средства Node.js, но это не заменяет независимый аудит всей системы.

Последний «подготовленный файл» в панели не доказывает, что браузер сохранил его или что существует внешняя копия. Автоматическое расписание и внешнее облачное хранилище пока не подключены. На бесплатном Render файл и данные могут пропасть, если копия не была скачана до обновления. Для рабочего сервиса нужны автоматические внешние копии, контроль ошибок и регулярная пробная проверка восстановления.

## Проверка и восстановление оператором

Нужен Node.js версии из `.node-version`. Установите зависимости из lockfile. Передавайте `PLATFORM_BACKUP_PASSWORD` через защищённый файл окружения (права 0600) или секреты менеджера служб, не аргументом командной строки. Не храните пароль рядом с единственной копией архива и не коммитьте файл окружения.

Пример содержимого отдельного приватного файла `.env.backup`:

```text
PLATFORM_BACKUP_PASSWORD=ВАШ_ПАРОЛЬ_КОПИИ
```

Проверка без восстановления:

```sh
node --env-file=.env.backup scripts/platform-backup.mjs --verify /protected/klarraum-platform.klrb
```

Восстановление в **новую, ещё не существующую** папку:

```sh
node --env-file=.env.backup scripts/platform-restore.mjs --source /protected/klarraum-platform.klrb --target /srv/klarraum-recovered
```

Исходная установка не изменяется. Существующая папка назначения отклоняется целиком. При неверном пароле, повреждении, пропавшем изображении, неправильной структуре или контрольной сумме результат не считается восстановленным. Данные сначала проверяются в закрытой временной папке, потом копируются в новую папку с закрытыми правами.

Структура результата:

```text
/srv/klarraum-recovered/director/director.sqlite
/srv/klarraum-recovered/director/companies/UUID/...
/srv/klarraum-recovered/legacy/...          # если основная установка входила в копию
/srv/klarraum-recovered/runtime.json       # приватные настройки; не публиковать
/srv/klarraum-recovered/RESTORE-INFO.json
```

При восстановлении все прежние директорские/владельческие/рабочие сессии удаляются, неиспользованные приглашения отзываются, секреты компаний меняются. Пароли активированных владельцев и работников сохраняются. Для сотрудников/владельцев, которые ещё не активировались, выдайте новые приглашения. Сам файл резервной копии и его исходные данные не переписываются.

Для отдельной платформы укажите `DIRECTOR_DATA_DIR=/srv/klarraum-recovered/director`. Адрес директора, базовый домен компаний, порт и `DIRECTOR_PASSWORD_HASH` задайте в приватной конфигурации хостинга; необходимые известные значения находятся в `runtime.json`. Можно задать новый пароль директора локальной командой `npm run admin:hash`.

Для подключённой демонстрации укажите `DATA_DIR=/srv/klarraum-recovered/legacy` и **отдельно** `DIRECTOR_DATA_DIR=/srv/klarraum-recovered/director`. Восстановленные настройки основного приложения находятся в `runtime.json` → `legacy`. В частности, возьмите изменённый `secret` для `APP_SECRET` и сохранённый `passwordHash` для `ADMIN_PASSWORD_HASH`, не старый `ADMIN_PASSWORD`: заново вычисленный из старого секрета хеш может отличаться. При изменении адреса настройте новый APP_ORIGIN. Не копируйте в чат значения хешей, секретов и ключей.

До переключения трафика: оставьте отправку писем и реальные заявки выключенными, запустите восстановленную установку на отдельном закрытом адресе, проверьте входы, две разные компании, клиентов/задания/отчёты, публичные и приватные изображения. Не запускайте две установки против одной папки SQLite. Только после проверки остановите старую службу и переключите хранилище/адреса. `runtime.json` не исполняется автоматически и не включает реальные заявки автоматически.

## Копирование из командной строки

Сначала остановите службу платформы, компании и основную установку, если она копируется. Маркер `.platform-running` блокирует обычную команду, пока директорская служба работает. После аварии маркер может остаться: убедитесь, что процессов действительно нет, прежде чем вручную убрать устаревший маркер. Он не является кластерной блокировкой и не обнаруживает произвольные внешние записи в базы.

```sh
node --env-file=.env.backup scripts/platform-backup.mjs --offline --data /srv/director-data --legacy-data /srv/main-data --runtime /protected/runtime-settings.json --destination /protected/new-platform-backup.klrb
```

`--legacy-data` необязателен для самостоятельной платформы. `--runtime` — приватный JSON с дополнительными настройками запуска, если их требуется перенести; без него сохраняются базы/изображения/внутренние настройки, а конфигурацию хостинга и пароль директора оператор задаёт отдельно. Самостоятельно искать и копировать все `.env` файлы по серверу команда не будет. Путь назначения не должен существовать; существующий архив не перезаписывается.

Предельные размеры первого формата: 2 GiB распакованных файлов, 512 MiB на отдельный файл, 100 000 файлов. При превышении нужен другой согласованный процесс резервирования; частичная копия не выдаётся как успешная. Скачивание в браузере держит готовый зашифрованный файл в памяти браузера, поэтому для больших объёмов используйте операторский процесс и внешнее хранилище.
